## 问题记录

本机正文取消/线程排队结果见 [HTTP专项记录](continued-0146-http.md)。桌面3/3、平板2/2已分别复现，以下结论按各自平台记录。

### C2：体检取消后旧正文占用线程，新检查排队（平板确认，P2，对应L2）

- 状态：已复现，未修复；界面取消立即响应，后台worker未立即释放。
- 步骤：先确认健康接口五项通过并读取按钮位置；设置`health_body_delay=20`，服务器发头与首字节后取消/重新体检；第二次正文开始后再取消，立即切到无延迟健康服务并第三次重启。
- 实际：第一轮服务端记录的前两次首字节事件分别为reset后188ms、1047ms；第三次点击前到客户端首次观察服务端收到健康请求为8641ms，第二轮为8687ms。这是包含ADB点击、截图、轮询的观察间隔；服务端对应第三次请求事件分别为reset后8594ms、8625ms，支持约8.6秒的启动延迟，不能当成精确worker排队测量。两轮最后都五项通过，没有实际播放开始上报。
- 影响：连续取消并重启时，新检查会停在等待线程，取消没有及时释放资源。不是凭`Future.cancelled`或UI已取消推断worker退出。
- 证据：`health-body.json`、`health-body-repeat.json`分别保留两轮时间；同名`health-body-third-start.png`、`health-body-third-complete.png`现为第二轮截图。等待期间五项均为「等待检查」，新健康请求的服务器响应本身很快。

### C3：Media3手动重新获取地址后返回原生播放链（平板确认，P2）

- 状态：已复现，未修复；本轮普通H.264合成片源，不据此推断真实P5色彩表现。
- 步骤：失效片源打开原生播放器 → 更多菜单选「系统解码重播」 → Media3首次及自动刷新均遭遇HTTP503 → 出现「片源连接失败」对话框 → 服务改为健康 → 点击「重新获取地址」。
- 实际：失败页是`SystemPlayerActivity`，点重新获取地址后转为`PlayerActivity`，没有继续使用Media3。`PlayerActivity`还会按`useVlc`选择VLC或系统原生引擎，本轮没有核验具体实例，不能单凭窗口类称为VLC。服务切健康并reset后，手动恢复阶段请求1次、视频请求成功1次、播放开始1次。
- 影响：按钮名称只承诺重新取地址，实际同时更换了解码路径；自动恢复保持Media3的已通过用例不能覆盖此手动分支。
- 证据：`media3-manual.json`、`media3-manual-failure.png`、`media3-manual-recovered.png`以及两次窗口类记录。
- 源码线索：`SystemPlayerActivity.retrySource()`不带recovery参数调用`EmbyPlayback.playItem()`；仅自动恢复分支沿用SystemPlayerActivity，普通手动H.264分支会启动PlayerActivity。

### C1：服务器数量返回后没有刷新（平板确认，P3）

- 状态：已复现，未修复；不影响已保存的服务器数据。
- 步骤：设置页原有3个服务器 → 添加合成服务器 → 管理列表立即显示4条 → 点「返回」回设置。
- 实际：概览和「Emby服务器」入口仍显示3，管理列表中实际为4。重新构建设置页后可刷新。
- 影响：新增/删除后页面数量会误导用户，入口仍能打开正确列表。
- 证据：`stale-add.json`、`server-list-four-after-add.png`、`settings-after-add.png`。本轮相同进程、相同0.1.146包实测。
- 源码线索：`ScrapedMainActivity.preferences()` / `SettingsLayout.summary()`构建时读取数量；返回时`onResume()`没有刷新这个设置快照。

以下为源码审查提供的待验证线索，尚不作为真机确认结论：
