## 本轮已核对证据

设备仅 OPD2401 / Android 16。测试使用本机 loopback 合成服务、合成账号和普通 H.264 视频。窗口类与解码画面分别核对，不能只凭视频请求计数断言已经播放。

| 场景 | 实测 |
| --- | --- |
| 原生失焦恢复 | 第二次 PlaybackInfo 延迟12s（短于15s读取超时），挂起时展开通知栏，确认焦点离开。旧连接约500ms后关闭，收起后产生第三次请求；合计3次请求、1次播放开始。实际视频帧时间17.667→33.833s |
| Media3 失焦恢复 | 同样延迟12s、3次请求、1次开始；旧连接约406ms后关闭，窗口仍为SystemPlayerActivity。视频帧时间15.250→30.542s |
| C4 在途取消后立即重连 | 第二次请求设为延迟25s，挂起期间按当前截图的「取消重连」并立即切健康重连。旧请求从到达到断开875ms，新请求点击前到观察到达391ms，健康对照312ms；第三次请求在原15s读取超时之前发生。继续观察超过原25s延迟，无迟到错误框、无额外重开，只有1次播放开始 |
| C2 快速连续取消 | 两次正文停顿均设20s，首字节到断开分别297ms、313ms；取消后马上重启，第三次健康请求点击前到观察到达343ms，最后五项通过、0次播放开始 |
| 主动取消不退还次数 | 自动刷新响应延迟12s，在挂起期间点取消，追加观察14s；始终2次播放信息、0次视频成功、0次播放开始，UI保持手动恢复入口；旧请求在约1094ms关闭 |
| 退出后延迟响应 | 刷新延迟8s，挂起期间退出到EmbyLibraryActivity，再观察10s；保持2次播放信息、0次播放开始，未重开播放器；旧请求约500ms关闭 |
| 已完成失败不退还次数 | fail下首次与一次自动刷新都已失败，再展开/收起通知栏并追加观察12s；仍只有2次播放信息、0次播放开始，没有第3次请求 |
| 分屏（部分通过） | 焦点在计算器时，首轮保持1次请求、不自动刷新；点回后允许一次刷新。已布局完成的终止卡片再次失焦仍完整可见，按当前隐藏控制栏坐标点「选择片源」能打开线路面板。首次进入后快速切走曾出现裁切，见O2，不计整体通过 |

计时包含 ADB 调用与轮询开销，不是精确 worker 退出时间。C4 的875ms是服务端所见请求存活时间（包含点击前采样），不是纯粹的点击到断开耗时。C2 本轮 configure→第三次请求296ms，两次断开均远早于20s正文恢复。

## O2：分屏首次进入后快速失焦的提示裁切（观察，待稳定复现与归因）

- 首次在ColorOS左右分屏内打开合成片，约0.6s后将计算器切到前台。焦点确在计算器，加载提示和首次终止卡片向左裁切；约40s后仍有裁切。点回播放器后布局恢复，已完成的失败卡片再次失焦则完整可见。
- 加载、首次失败采样分别为 `split-unfocused-loading.png`、`split-unfocused-loading-later.png`；恢复布局后失焦采样为 `split-unfocused-terminal.png`。
- 稳定布局后的另一轮对照，加载提示失焦后完整可见（`split-settled-after-focus.png`）。这支持时序/系统窗口切换相关的观察，但尚未证明具体根因，也没有确认是0.1.147新引入的回归。
- 未修改应用代码尝试掩盖现象，不把分屏整体标为通过。接续应先稳定复现早期失焦与ColorOS窗口尺寸/位置更新的关系，再决定修复。

## 测试脚本与证据边界

原始 JSON、截图与 XML 只保存在忽略目录 `deliverables/tablet-0147-boundary/`；原有 C1–C4 的记录保留在 `deliverables/tablet-0147/`。服务器管理页只保存数量，不持久化真实地址。

本轮最初进度采样误把顶端时钟当作播放时间，另有 XML 临时文件清理失败。改用独立临时文件后，控制栏仍会在 UI 树采集结束前隐藏，因此最后人工核对了两张实际视频帧内的时间戳。这些属于脚本采样问题，不算软件失败，也不凭空增加真机通过次数。

分屏自动化还有两项限制：ColorOS的UI树只给当前焦点窗口，不能以“没找到另一窗口节点”推断未分屏；控制栏显隐会移动失败卡片按钮，最终按当时截图的隐藏控制栏坐标确认按钮可用。一次分屏配置重建返回了服务器列表，误采的本地截图已删除，不提交任何真实地址截图。

O1（原生侧栏系统返回退出播放器）、真实杜比 P5、HDR 和真实服务器转码不在本轮通过范围。
