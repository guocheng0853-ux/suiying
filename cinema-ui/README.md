# 随影 0.1.48 P2P 加速

原 TorrentEngine 的 libtorrent 会话几乎全是默认值：上传限 128KB/s，而 BT 是“多上传才能多下载”，限得太低会拖慢下载；磁力链接只带 3 个 tracker。

本版在主 DEX 插入两处调用（设置 →“P2P 加速”，默认开）：
- 会话新建后调用 `TorrentBoost.tune`：上传上限 512KB/s；每秒发起连接数 30→80；新任务立即尝试的连接 30→60；连接超时 15→7 秒；请求队列 500→1500；连接上限 300；开启局域网发现（LSD）和路由器端口映射（UPnP / NAT-PMP）；向所有 tracker、所有层级 announce。
- 下载磁力链接前调用 `TorrentBoost.magnet`：追加 ngosang/trackerslist 当日最佳列表里的 21 个公共 tracker，去重，不改 info hash 和原有 tracker。

版本 0.1.48 / code 49。

**验证范围**：
- 已做：补丁自检通过，两处被改方法去掉插入的调用后，操作码和引用与原来逐条一致，其余 11797 个方法体完全不变。`TorrentBoostTest` 验证 tracker 追加、去重、开关和幂等。
- 未做：libtorrent 原生库无法在 JVM 上运行，设置是否生效、实际能快多少都没有测，取决于种子的做种人数和网络环境（运营商 NAT、UDP 是否受限）。没有 Android 真机实测。

# 随影 0.1.47 多线程加速

**多线程分段加速**（设置 → “多线程加速”，默认开）：
- 网盘类直链通常按单个连接限速。开启后，远程 HTTP(S) 地址都经本机代理；本机地址（如影视仓组件自带的代理）不经过。
- 对服务器确认支持 Range、且不小于 8MB 的文件，同时开 4 个连接、按 1MB 分段预取，再按顺序写给播放器；预取窗口 8 段（约 8MB 内存）。
- 拖动时播放器发来的 Range 照常透传；播放器断开即整组取消。
- m3u8 和小文件仍原样转发。服务器不支持 Range 时，退回单连接转发。

**开播等待**：
- 播放前地址检查的等待上限由最多 12 秒压到 4 秒，超时直接开播（记为“未确认”）。
- 代理读完的上游连接交回连接池复用，HLS 每个分片不再重新握手。

版本 0.1.47 / code 48。

**验证范围**：
- 已做：`RangeAcceleratorTest` 在 JVM 上用每连接限速 2MB/s、必须带 Cookie 的本机源站测试：单连接下载 16MB 用 8.1 秒，经代理 4 连接用 2.0 秒（约 4 倍），SHA-256 一致；中间位置 Range、小区间、无 Range 服务器转发都正确；ffmpeg 经加速代理把 11.6MB 的 MP4 全部 400 帧解出。构建、签名、DEX 补丁自检和 19 个单元测试通过。
- 未做：没有 Android 真机或真实网盘实测。实际提速取决于网盘是否按连接限速、是否限制并发；如果视频由小雅服务器中转，上限是服务器带宽，多线程无法突破。

# 随影 0.1.46 播放链路检查与 Stremio 分组选源

**播放链路断点（已查实；本版加入修复，JVM 验证、未真机）**：打包的 LibVLC 是 3.0.22，只支持 `:http-user-agent` 和 `:http-referrer`；原播放器把其他请求头写成 `:http-header=`，而 LibVLC 3 没有这个选项，会直接忽略。所以线路声明的 Cookie、Origin、Authorization 等请求头从来没有发到服务器，这类线路会出现“详情能开、地址能取、就是放不出”。另外原实现按 `"User-Agent"` 精确取值，小写的 `user-agent` 会被丢掉。

本版在主 DEX 的 `VlcPlayback.setSource` 开头前插 4 条指令，调用 `HeaderRoute`：
- 只有存在 VLC 无法携带的请求头时，才把地址改走本机代理（只监听 127.0.0.1，路径带随机令牌），由代理补齐全部请求头。
- m3u8 里的子列表、分片、`#EXT-X-KEY`、`#EXT-X-MAP` 地址一并改写；MP4 拖动透传 Range。
- 其余主 DEX 方法体逐指令不变（构建时自检）。

**播放前真实地址检查**：影视仓详情选集、播放器内换源、Stremio 直链在开播前都会带着线路请求头取首字节：
- 识别 MP4、MKV、FLV、TS、m3u8、网页、JSON、HTTP 错误；m3u8 会继续读子列表和首个分片。
- 明确不是视频时（HTTP 错误、网页、JSON、空响应）提示“返回换源 / 仍然播放”。播放器内换源和自动换源遇到这种情况不会切换。
- 网络超时等未确认情况仍交给播放器尝试。
- 结果写入“设置 → 故障排查 → 播放地址检查记录”（最近 30 条，只记主机名）。“有视频数据”不等于能解码。

**影视仓网页解析**：以前 `parse=1` 和 `jx=1` 的线路一律报“尚未支持”。现在的处理：
- `parse=1`：用不可见 WebView 打开播放页，拦截页面实际请求的视频地址，并带上 Referer、UA、Cookie。
- `jx=1`：依次尝试配置里 `parses` 的前 3 个（JSON 接口直接取地址，其余走嗅探）。
- `parse=0` 但检查发现地址返回的是网页时，自动改为嗅探。
- 证书错误不放行，不开放 JS 桥。页面可能先请求广告视频，嗅探拿的是第一个命中的地址。

**Stremio 选源**：覆盖原 `streams()`，改为按插件分组的弹窗，手机从底部弹出、平板居中，深浅主题都适配：
- 3 路并发，每个插件 25 秒预算（超时主动断开），显示等待、查询中、条目数、无条目、失败原因，可折叠、单个插件重试或全部重试。
- 关闭弹窗即作废后台结果。
- 条目标注直链 / P2P / 外部网页 / YouTube 不支持；选中后走原 `play()`（原播放器、原换源队列）。

预置源保持为空，TorrentClaw 专用入口保持移除；用户自定义接口、插件、观看记录不变。版本 0.1.46 / code 47。

**验证范围**：
- 已做：APK 编译、签名、类解析和三处 DEX 补丁逐指令自检通过，18 个单元测试通过。
- `HeaderRouteTest` 在 JVM + ffmpeg 上用本机源站（必须带 Cookie + Origin）验证：只带 UA/Referer 时被 403 拒绝；经代理后 ffmpeg 从“主列表 → 子列表 → AES-128 加密分片”实际解码出 150 帧；MP4 拖动走 Range/206；地址检查能区分视频、403、网页、JSON、404 和网络失败。
- 未做：这些测试不是 Android / LibVLC 实测。本轮云端出网被拦，访问不到小雅、Stremio 插件和各影视站；用户电脑也未连上，所以没有对任何真实来源做播放验证。WebView 嗅探、分组弹窗界面、本机代理在 Android 上的表现均未真机测试。

构建：仓库根目录执行 `sh scripts/setup_build_tools.sh`（只从 GitHub 下载 jadx 内置的 D8 和 apksig、apktool 内置的 aapt2、Android 35 android.jar；ecj 用 JDK javac 兼容层代替；zipalign 用支持 `-P 16` 的 Python 实现），然后执行 `python3 cinema-ui/build_ui.py`、`python3 cinema-ui/verify_apk.py`、`sh scripts/run_tests.sh`。签名需要本地放回 `cinema-ui/signing.jks`；`assets/fusion-default.json`（含个人令牌）不入库，缺失时使用脱敏样例。
