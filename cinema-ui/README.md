# 随影 0.1.121 Emby HTTP 409、播放身份统一、断点保护（code 122，未真机验证）

- **HTTP 409 / 服务器拒绝时说清原因**：Emby 返回非 2xx 时，把服务器正文里的那句话（JSON 的 Message、或去掉标签的网页文字，网址和疑似令牌隐去，最多 80 字）带进提示和调试信息；409 单独说明「共享服务器常限制同时播放路数或设备数」。
- **不再自己占名额**：记住最近一路没回报停止的 Emby 播放（VLC 和内置杜比播放都算），换片、换播放器、切版本、重新获取地址之前先通知服务器停止，转码中的再结束转码。请求播放信息遇到 409 时先清理残留、等 2 秒重试一次。
- **播放身份统一**：内置杜比播放（Media3）默认 User-Agent 从 Mozilla/5.0 改为和 VLC 播放、离线下载相同的 MediaPocket/0.1.3，避免出现「VLC 能播、内置播放被拒」。片源自带 User-Agent 时仍以片源为准。
- **断点保护**：服务器忽略 Range 时，内置播放最多跳过 64 MB，超过就提示「服务器不支持从中间读取，请从头播放或换线路」，不再为了拖动白下几个 GB。

继承 0.1.120。

# 随影 0.1.100 允许官方客户端名的 Emby 登录（code 101）

有的 Emby 只放行指定客户端。添加服务器时原来固定 `Client="MediaPocket"`。这类服务器对 `/Users/AuthenticateByName` 返回 HTTP 403，正文是「请使用群公告中允许的客户端进行访问」。旧代码把 401 和 403 都收成 `HTTP 401`，界面就写成「用户名或密码不正确」。账号可以没有密码，空密码本身是对的。

现在仍先用 MediaPocket，已经接受这个名字的服务器不变。只有这种明文的客户端拒绝才再请求一次，改用官方名称 `Client="Emby"`，不写死 Hills。成功后这个服务器记住 Emby，之后的接口用这个名字。播放地址加上 `X-Emby-Client=Emby`，因为不带允许的客户端名时直链同样是 403；令牌仍只放在 `api_key`，不放进请求头，也不写进日志。仍被拒绝时显示服务器原文；原文不可读时显示「服务器不允许这个客户端」。真正的 HTTP 401 还是「用户名或密码不正确」。

此前在用户指定的 Emby 4.9.5.0 测试服务器上核对过 403 和 200（地址与服务器名称不写入公开仓库）：`Client="MediaPocket"`、`Client="Infuse"` 为 403 且正文如上；`Client="Emby"` 对无密码账号为 200；同一客户端配错误密码为 401，正文「用户名或密码无效。请重试。」。不带客户端名的视频直链为 403，带 `X-Emby-Client=Emby` 为 206。`EmbyApiTest` 覆盖只回退一次、401 仍是密码文案、403 显示服务器原文。没有在真机安装这个版本。

 # 随影 0.1.82 弹幕匹配、字幕扩展名、外部中文路径与深链修复

弹幕自动匹配在集数标题是「第2话」这类写法时选不中。同集判断的正则用 `\b` 词边界，这台构建机的 JDK 上中日文字符被当成词字符，边界永不成立，自动匹配返回空后只能手动选。现在改用数字环视（`(?<!\d)` / `(?!\d)`），只看数字邻居，不依赖 `\b` 的词字符定义；「第12话」「第01话」能对上，「第21话」不会误配成第 2 集。规则测试补了这些用例。

在线字幕下载落盘时，名字里没有扩展名一律补 `.srt`：ASS 字幕会以 .srt 后缀保存，靠扩展名分发格式的路径会错。现在解压后按内容判断——`[Script Info]` 存 .ass，`WEBVTT` 存 .vtt，其余 .srt；名字以 .zip 结尾时剥掉再按内容补。已记住的字幕选择不受影响。

系统里用「随影 (VLC)」打开视频，文件管理器经常传未经编码的原始路径（中文、空格直接拼在 file:// 里）。`java.net.URI` 对这种地址直接抛异常，之前会提示「这个地址不能用随影播放」。现在解析失败时退回前缀和文件名判断：http/https/file/content 前缀加视频扩展名即放行，标题也从原始路径取。已在真机用「随影 测试.mp4」这样的路径实测，正常进入播放器播放。

`suiying://import` 深链接打开时会在浏览器任务栈里再开一个首页实例，应用内已有实例不被复用，`onNewIntent` 不生效。主 Activity 现在是 `singleTask`，深链复用现有实例。

播放页 250ms 轮询里弹幕每次都整帧重绘并重读全部配置。现在只更新进度，配置有变化才重排版；样式改动最迟 250ms 生效。

测试 59 项全部通过（含新增 9 条断言）。Windows 上从本机 SDK 出包，adb 覆盖安装到 ColorOS 真机：启动、外部打开原始中文路径均无崩溃。

审查 0.1.72 的 Emby 接入后修正：

- **令牌不再发给外部主机**：播放地址的请求头里原来带 `X-Emby-Token`，本地代理跟随 302 跳转时会把请求头一起带到网盘/CDN 主机（Emby 挂网盘、302 直链的常见配置）。现在令牌只放在本服务器地址的 `api_key` 参数里，请求头不带。媒体源 `Path` 是外部地址（.strm 远程链接）时，原来会直接在外部地址后面加 `api_key`，现在改走服务器的 `/Videos/{id}/stream?static=true`，由服务器自己跳转；外部主机的字幕、转码地址也不加 `api_key`。判断按主机名加端口。
- **续播不再跳两次**：PlaybackInfo 原来带 `StartTimeTicks`（续播位置），转码流会从该位置开始，播放器又按记录的进度再跳一次，结果跳到两倍位置。现在 PlaybackInfo 一律从 0 开始，续播只靠播放器跳转。
- **媒体库分页**：原来只请求前 80 条，大媒体库后面的片子看不到。现在每页 100 条，底部「加载更多（已显示 n / 总数）」继续加载。

# 随影 0.1.64 影视仓磁力选集与简介实体

详情页状态行「读取失败：仅支持 HTTP / HTTPS 地址」不是详情接口失败。选集点下去之后，`FusionLibraryActivity.play` 把爬虫返回的播放地址交给 `TvBoxPlay`，而 `TvBoxPlay` 对所有地址都调用 `TvBoxRules.resolve`。这个检查是给配置、jar 和直播列表用的，只接受 HTTP/HTTPS。磁力选集（`magnet:?xt=urn:btih:…`，页面上显示成「此磁力源是边下载边播」）因此在详情页被记成读取失败，到不了播放器。

# 随影 0.1.60 修复 P2P 已缓存却卡在开头

现象（2026-10-16 截图）：P2P 有 206 个连接、2.6MB/s、已缓存 112MB，进度却停在 00:03。

原因：0.1.50 把 `VerifiedPieceReader` 改成缺片段时“先返回已验证的前半段”（短读）。但 `ProxyFileDescriptorCallback.onRead` 的约定是“必须返回请求的全部字节，除非到达文件末尾”；Android 的 AppFuse 是带页缓存的 FUSE，没有 `FOPEN_DIRECT_IO`，短读会被内核当成 EOF。所以 VLC 读到第一个还没下完的片段就以为文件结束或读到了空数据。

修复：恢复为整块读取。缺片段时等它校验完成再返回，等待期间每 2 秒重新提高该片段的优先级。超时仍抛 EIO，绝不返回不完整或补零的数据。`PieceReadsTest` 改为断言“片段到齐后返回完整长度，缺失时报错而不是短读”。

版本 0.1.60 / code 61。44 个测试通过，构建、签名、DEX 补丁自检通过。没有真机复测（libtorrent 原生库和 AppFuse 只能在 Android 上运行）。

# 随影 0.1.47 多线程加速

**多线程分段加速**（设置 → “多线程加速”，默认开）：
- 网盘类直链通常按单个连接限速。开启后，远程 HTTP(S) 地址都经本机代理；本机地址（如影视仓组件自带的代理）不经过。
- 对服务器确认支持 Range、且不小于 8MB 的文件，同时开 4 个连接、按 1MB 分段预取，再按顺序写给播放器；预取窗口 8 段（约 8MB 内存）。
- 拖动时播放器发来的 Range 照常透传；播放器断开即整组取消。
- m3u8 和小文件仍原样转发。服务器不支持 Range 时，退回单连接转发。

**开播等待**：
- 播放前地址检查的等待上限由最多 12 秒压到 4 秒，超时直接开播（记为“未确认”）。
- 代理读完的上游连接交回连接池复用，HLS 每个分片不再重新握手。

版本 0.1.47 / code 48。

# 随影 0.1.46 播放链路检查与 Stremio 分组选源

**播放链路断点（已查实；本版加入修复，JVM 验证、未真机）**：打包的 LibVLC 是 3.0.22，只支持 `:http-user-agent` 和 `:http-referrer`；原播放器把其他请求头写成 `:http-header=`，而 LibVLC 3 没有这个选项，会直接忽略。所以线路声明的 Cookie、Origin、Authorization 等请求头从来没有发到服务器，这类线路会出现“详情能开、地址能取、就是放不出”。另外原实现按 `"User-Agent"` 精确取值，小写的 `user-agent` 会被丢掉。

本版在主 DEX 的 `VlcPlayback.setSource` 开头前插 4 条指令，调用 `HeaderRoute`：
- 只有存在 VLC 无法携带的请求头时，才把地址改走本机代理（只监听 127.0.0.1，路径带随机令牌），由代理补齐全部请求头。
- m3u8 里的子列表、分片、`#EXT-X-KEY`、`#EXT-X-MAP` 地址一并改写；MP4 拖动透传 Range。
- 其余主 DEX 方法体逐指令不变（构建时自检）。

**播放前真实地址检查**：影视仓详情选集、播放器内换源、Stremio 直链在开播前都会带着线路请求头取首字节：
- 识别 MP4、MKV、FLV、TS、m3u8、网页、JSON、HTTP 错误；m3u8 会继续读子列表和首个分片。
- 明确不是视频时（HTTP 错误、网页、JSON、空响应）提示“返回换源 / 仍然播放”。播放器内换源和自动换源遇到这种情况不会切换。
- 网络超时等未确认情况仍交给播放器尝试。
- 结果写入“设置 → 故障排查 → 播放地址检查记录”（最近 30 条，只记主机名）。“有视频数据”不等于能解码。

**影视仓网页解析**：以前 `parse=1` 和 `jx=1` 的线路一律报“尚未支持”。现在的处理：
- `parse=1`：用不可见 WebView 打开播放页，拦截页面实际请求的视频地址，并带上 Referer、UA、Cookie。
- `jx=1`：依次尝试配置里 `parses` 的前 3 个（JSON 接口直接取地址，其余走嗅探）。
- `parse=0` 但检查发现地址返回的是网页时，自动改为嗅探。
- 证书错误不放行，不开放 JS 桥。页面可能先请求广告视频，嗅探拿的是第一个命中的地址。

**Stremio 选源**：覆盖原 `streams()`，改为按插件分组的弹窗，手机从底部弹出、平板居中，深浅主题都适配：
- 3 路并发，每个插件 25 秒预算（超时主动断开），显示等待、查询中、条目数、无条目、失败原因，可折叠、单个插件重试或全部重试。
- 关闭弹窗即作废后台结果。
- 条目标注直链 / P2P / 外部网页 / YouTube 不支持；选中后走原 `play()`（原播放器、原换源队列）。

预置源保持为空，TorrentClaw 专用入口保持移除；用户自定义接口、插件、观看记录不变。版本 0.1.46 / code 47。
